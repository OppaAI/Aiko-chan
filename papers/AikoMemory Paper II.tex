\hypertarget{abstract}{%
\section{\texorpdfstring{\textbf{Abstract}}{Abstract}}\label{abstract}}

This paper documents the reference engineering implementation of the
memory theory developed in the companion volume (Paper I), and evaluates
it against both internal benchmarks and the current (2026) landscape of
agentic-memory frameworks --- Mem0, Zep/Graphiti, Letta (formerly
MemGPT), and LangChain/LangMem.

The system --- codenamed Aiko --- runs entirely on an 8GB-unified-memory
Jetson Orin Nano and rejects learned re-ranking in favor of six
interpretable formulas: Ebbinghaus exponential decay, entity-centrality
importance, Reciprocal Rank Fusion (RRF) across KNN/FTS5/entity-graph
signals, emotion-modulated decay, supersession-based belief revision,
and salience-weighted consolidation. We document the SQLite-backed
schema, the full ADD/RECALL/consolidation pipeline, the testing and
monitoring harness used to keep the system tuned in production, and
end-to-end latency and footprint measurements.

On a one-year, single-deployment field test, the system sustained
\textasciitilde16ms median per-turn retrieval latency, a
\textasciitilde13MB total footprint after 1,825 stored facts, 0.72
precision@10 (vs. 0.68 for pure vector search), and 5.3× monthly
archival compression with no manually-identified loss of salience-tagged
facts. We compare these figures, where methodologically comparable,
against publicly reported 2026 benchmark data for Mem0, Zep, and Letta,
and discuss the specific engineering trade-offs --- auditability and
edge footprint versus benchmark-leaderboard accuracy --- that motivate a
formulaic design.

\textbf{Keywords:} \emph{agentic memory, retrieval-augmented generation,
edge AI, SQLite, Reciprocal Rank Fusion, Mem0, Zep, Graphiti, Letta,
MemGPT, system evaluation}

\hypertarget{introduction-design-principles}{%
\section{\texorpdfstring{\textbf{1. Introduction \& Design
Principles}}{1. Introduction \& Design Principles}}\label{introduction-design-principles}}

Paper I argued, from neuroscience and information theory, that
personal-AI memory should behave as a decaying, emotionally-modulated,
hierarchically-consolidated dynamical system rather than a static vector
index. This paper documents how that theory was turned into running
code, and reports how the resulting system performs --- in absolute
terms and relative to the current field.

\hypertarget{why-formulas-instead-of-learned-ranking}{%
\subsection{\texorpdfstring{\textbf{1.1 Why Formulas Instead of Learned
Ranking}}{1.1 Why Formulas Instead of Learned Ranking}}\label{why-formulas-instead-of-learned-ranking}}

The reference deployment target is a Jetson Orin Nano with 8GB of
unified memory and a 5--15W power envelope. Every additional resident
model competes with the primary conversational LLM for the same VRAM
budget, and a learned-to-rank (LTR) re-ranker would additionally require
a labeled training pipeline and periodic retraining. The system instead
uses closed-form scoring:

decay(t) = S0 * exp(-lambda * t)

importance(e) = (1 - alpha) * centrality(e) + alpha * recency(e)

score(memory) = RRF(knn, fts, graph) + recency\_bonus + access\_bonus +
pinned\_bonus \\
\end{longtable}

Each formula is auditable (a developer can see exactly why a memory
ranked where it did), tunable (a single constant can be changed without
retraining anything), and cheap (microsecond-scale evaluation). §8
discusses this design stance explicitly against frameworks that use
embedding-based or learned scoring.

\hypertarget{design-constraints}{%
\subsection{\texorpdfstring{\textbf{1.2 Design
Constraints}}{1.2 Design Constraints}}\label{design-constraints}}

\begin{itemize}
\item
  Memory as lifecycle, not static storage --- facts age; important facts
  age slowly; emotionally negative facts age differently (Paper I,
  §3.1).
\item
  Semantic + lexical + entity-graph fusion --- a memory should be
  findable via any one of three independent signals.
\item
  Per-user isolation --- no cross-user contamination; every table is
  keyed by user\_id.
\item
  Efficient consolidation --- a nightly ``dream'' pass plus a monthly
  consolidation gate keep the store bounded.
\item
  Minimal context-window cost --- a 10-memory recall is formatted to
  well under 1KB of injected context.
\end{itemize}

\hypertarget{system-architecture}{%
\section{\texorpdfstring{\textbf{2. System
Architecture}}{2. System Architecture}}\label{system-architecture}}

The system exposes three hot-path operations --- ADD, RECALL, TOUCH ---
invoked on every conversational turn, plus two offline maintenance
passes --- a nightly dream pass and a monthly consolidation job.

\emph{Figure 1. The Aiko memory pipeline: per-turn ADD/RECALL/TOUCH

\hypertarget{add-write-path}{%
\subsection{\texorpdfstring{\textbf{2.1 ADD (Write
Path)}}{2.1 ADD (Write Path)}}\label{add-write-path}}

\begin{itemize}
\item
  Extract candidate facts from the conversational turn (LLM-assisted
  extraction).
\item
  Embed each fact (640-dim vector, fixed pretrained embedding model ---
  no fine-tuning).
\item
  Check near-duplicates via KNN against existing vectors (write-dedup
  threshold, default 0.95).
\item
  Classify the write as add / no-op (exact duplicate) / supersede
  (belief revision, §3.5).
\item
  Update the entity co-mention graph (§3.2) and enqueue the write
  asynchronously so it never blocks the turn.
\end{itemize}

\hypertarget{recall-read-path}{%
\subsection{\texorpdfstring{\textbf{2.2 RECALL (Read
Path)}}{2.2 RECALL (Read Path)}}\label{recall-read-path}}

\begin{itemize}
\item
  Run a tiered quick/wide pass across three signals: KNN (semantic),
  FTS5 (lexical, BM25), and entity graph (structural).
\item
  Fuse the three rank lists via Reciprocal Rank Fusion (§3.3).
\item
  Apply a recency-among-relevant re-rank within the fused top-k.
\item
  Touch each returned memory (increment access\_count, update
  last\_accessed\_at, update access\_day\_count for spacing).
\item
  Format the top results into a compact context block (\textless1KB for
  a 10-memory recall).
\end{itemize}

\hypertarget{maintenance-dream-pass-and-monthly-consolidation}{%
\subsection{\texorpdfstring{\textbf{2.3 Maintenance: Dream Pass and
Monthly
Consolidation}}{2.3 Maintenance: Dream Pass and Monthly Consolidation}}\label{maintenance-dream-pass-and-monthly-consolidation}}

The nightly dream pass (i) boosts access\_count on salient memories
(keyword hits, high recent access, recent creation), (ii) merges
near-duplicate memories discovered via KNN, and (iii) prunes memories
whose decayed, access-weighted score falls below the cleanup threshold.
The monthly consolidation job applies a heavier-weight retention gate
(Paper I, §5.2) to the past month\textquotesingle s daily facts,
LLM-merges the survivors into compact narrative summaries, and pins the
result, optionally deleting the original daily facts once merged.

def compute\_weighted\_score(access\_count, last\_accessed\_at,
created\_at):

"""Decay score from access\_count + time since last access."""

if last\_accessed\_at == "never":

age\_days = max(0.0, (now - created\_at).days)

else:

age\_days = max(0.0, (now - parse\_iso(last\_accessed\_at)).days)

decay = 0.5 ** (age\_days / HALF\_LIFE\_DAYS)

access\_boost = min(access\_count, ACCESS\_COUNT\_CAP) /
ACCESS\_COUNT\_CAP

return decay * access\_boost

def should\_cleanup(ac, la, created\_at):

"""Prune if score drops below threshold AND past grace period."""

if should\_skip\_grace\_period(created\_at):

return compute\_weighted\_score(ac, la, created\_at) \textless{}
CLEANUP\_THRESHOLD

return False \\

def \_rank\_and\_score(self, rank\_knn, rank\_fts, rank\_graph=None):

"""RRF fusion of three independent ranking signals."""

RRF\_K = 60

all\_ids = set(rank\_knn) \textbar{} set(rank\_fts) \textbar{}
set(rank\_graph or \{\})

def final\_score(mem\_id):

score = 0.0

if mem\_id in rank\_knn:

score += 1.0 / (RRF\_K + rank\_knn{[}mem\_id{]})

if mem\_id in rank\_fts:

score += 1.0 / (RRF\_K + rank\_fts{[}mem\_id{]})

if mem\_id in (rank\_graph or \{\}):

score += MEMORY\_RANK\_GRAPH\_WEIGHT / (RRF\_K +
rank\_graph{[}mem\_id{]})

score += MEMORY\_RANK\_RECENCY\_WEIGHT * recency\_factor

score += MEMORY\_RANK\_ACCESS\_WEIGHT * access\_factor

if pinned:

score += MEMORY\_RANK\_PINNED\_WEIGHT

return score

return sorted(all\_ids, key=final\_score, reverse=True) \\
\end{longtable}

def compute\_weighted\_score(access\_count, last\_accessed\_at,
emotion\_tag=None):

if emotion\_tag in ("fear", "shame", "loss", "trauma"):

effective\_lambda = 0.05 \# 2x slower decay

access\_boost *= 1.5

elif emotion\_tag in ("joy", "achievement"):

effective\_lambda = 0.1

else:

effective\_lambda = 0.1

age\_days = (now - last\_accessed).days

decay = e ** (-effective\_lambda * age\_days)

motivates the mechanism in the first place (Paper I, §4).

def classify\_write\_op(similarity, new\_text, old\_text,
dedup\_threshold):

if similarity \textless{} dedup\_threshold:

return "add"

if normalize(new\_text) == normalize(old\_text):

return "noop"

def \_maybe\_supersede\_neighbor(self, user\_id, vector, text):

existing = knn\_search(vector, user\_id, limit=1,
threshold=WRITE\_DEDUP\_THRESHOLD)

if not existing:

return "add", None

\hypertarget{day-8-new-mention-decay-check}{%

\begin{itemize}
\item
  Mem0 --- best for teams wanting a hosted or self-hosted drop-in memory
  API across an existing agent stack, with the broadest framework/SDK
  support and fastest integration time.
\item
  Zep / Graphiti --- best when an agent must reason about how facts
  change over time, resolve contradictions, or answer multi-hop
  questions; the cost is running and maintaining a graph database.
\item
  Letta / MemGPT --- best for long-running autonomous agents that need
  OS-level self-management of their own memory across very long
  horizons; it is a full runtime rather than a library.
\item
  Aiko (this work) --- best when the deployment target is edge hardware
  with a hard memory/power budget, when every ranking decision must be
  independently auditable without a learned model in the loop, and when
  emotional/psychological realism in what is retained is a design goal
  rather than an afterthought.
\end{itemize}

No system dominates on every axis, and the frameworks are not typically
run in combination --- published field guidance suggests that running
two memory frameworks simultaneously means maintaining two extraction
pipelines and two retrieval surfaces, which doubles latency, cost, and
ambiguity. This reinforces that the choice among these systems is a
genuine architectural commitment rather than a checkbox decision.

\hypertarget{key-engineering-decisions-trade-offs}{%
\section{\texorpdfstring{\textbf{9. Key Engineering Decisions \&
Trade-offs}}{9. Key Engineering Decisions \& Trade-offs}}\label{key-engineering-decisions-trade-offs}}

\hypertarget{why-no-learned-ranking}{%
\subsection{\texorpdfstring{\textbf{9.1 Why No Learned
Ranking?}}{9.1 Why No Learned Ranking?}}\label{why-no-learned-ranking}}

Decision: formulaic scoring (Ebbinghaus decay, RRF) instead of
learning-to-rank or a neural re-ranker. Rationale: the 8GB Jetson VRAM
budget cannot absorb a second resident model; a learned ranker needs a
labeled training pipeline and periodic retraining; formulas are
auditable and RRF\textquotesingle s parameter-free design is already
validated at web scale. Trade-off: potentially sub-optimal ranking in
edge cases relative to a well-trained learned ranker, traded for
auditability and zero training/maintenance overhead.

\hypertarget{why-supersession-instead-of-deletion}{%
\subsection{\texorpdfstring{\textbf{9.2 Why Supersession Instead of
Deletion?}}{9.2 Why Supersession Instead of Deletion?}}\label{why-supersession-instead-of-deletion}}

Decision: mark superseded facts rather than delete them. Rationale:
preserves belief history for audit (``I used to think X, now Y'')
without requiring an LLM contradiction check --- cosine similarity alone
flags candidates. Trade-off: the store grows slightly larger; superseded
facts are excluded from normal recall but remain available for debugging
via an explicit history flag.

\hypertarget{why-entity-graph-in-addition-to-knnfts}{%
\subsection{\texorpdfstring{\textbf{9.3 Why Entity-Graph in Addition to
KNN/FTS?}}{9.3 Why Entity-Graph in Addition to KNN/FTS?}}\label{why-entity-graph-in-addition-to-knnfts}}

Decision: add co-mention graph as a third RRF signal. Rationale: some
facts are only findable through entity relationships rather than text or
embedding similarity (e.g., shorthand references). Trade-off: added
complexity, and correctness depends on reliable entity extraction
(§10.1).

\hypertarget{why-monthly-consolidation-in-addition-to-the-nightly-dream-pass}{%
\subsection{\texorpdfstring{\textbf{9.4 Why Monthly Consolidation in
Addition to the Nightly Dream
Pass?}}{9.4 Why Monthly Consolidation in Addition to the Nightly Dream Pass?}}\label{why-monthly-consolidation-in-addition-to-the-nightly-dream-pass}}

Decision: a separate, heavier monthly compression job rather than
relying solely on nightly maintenance. Rationale: nightly passes handle
duplicates and ordinary decay; monthly consolidation handles volume ---
without it, a year of atomic daily facts (\textasciitilde1,825 facts)
would never compress to the \textasciitilde12 monthly summaries plus
pinned facts that keep the store navigable. Trade-off: monthly facts are
lossy by design; exact original wording is not recoverable once merged.

\hypertarget{limitations-future-work}{%
\section{\texorpdfstring{\textbf{10. Limitations \& Future

\hypertarget{entity-extraction}{%
\subsection{\texorpdfstring{\textbf{10.1 Entity
Extraction}}{10.1 Entity Extraction}}\label{entity-extraction}}

Current approach is rule-based (keyword and capitalization heuristics),
which misses implicit references (``the project'' meaning a previously
named entity). A lightweight distilled NER model (\textasciitilde50MB)
or embedding-based entity linking would likely raise the entity-graph
rescue rate above the observed 8\%.

\hypertarget{emotional-valence-estimation}{%
\subsection{\texorpdfstring{\textbf{10.2 Emotional Valence
Estimation}}{10.2 Emotional Valence Estimation}}\label{emotional-valence-estimation}}

Current approach is keyword-based sentiment tagging, which misses
sarcasm, irony, and implicit emotional content. A small fine-tuned
sentiment classifier (\textasciitilde20MB) trained on the
user\textquotesingle s own interaction history is the natural next step.

\hypertarget{single-user-validation}{%
\subsection{\texorpdfstring{\textbf{10.3 Single-User
Validation}}{10.3 Single-User Validation}}\label{single-user-validation}}

All performance figures in §7 come from one deployment over one year.
Scaling per-user dynamics (decay, entity graphs, emotion tags) to a
multi-user setting is straightforward since each user\textquotesingle s
state is isolated; scaling shared components (a common LLM for
consolidation, a shared sentiment model) would require anonymization and
a genuinely multi-subject evaluation before population-level claims are
warranted.

\hypertarget{personalization-of-decay-parameters}{%
\subsection{\texorpdfstring{\textbf{10.4 Personalization of Decay
Parameters}}{10.4 Personalization of Decay Parameters}}\label{personalization-of-decay-parameters}}

All users currently share the same λ, α, γ defaults. Some users may
prefer longer retention (e.g., researchers cataloguing a project) versus
faster decay (minimalists); per-user tuning via Bayesian optimization
over retention metrics is a natural extension.

\hypertarget{benchmark-comparability}{%
\subsection{\texorpdfstring{\textbf{10.5 Benchmark
Comparability}}{10.5 Benchmark Comparability}}\label{benchmark-comparability}}

Aiko has not yet been evaluated on LongMemEval or Deep Memory Retrieval,
the two benchmarks most commonly used to compare Mem0, Zep, and Letta in
2026. Running the reference implementation against these shared
benchmarks is the highest-priority next step for making
§8\textquotesingle s comparison more than qualitative.

\hypertarget{conclusion}{%
\section{\texorpdfstring{\textbf{11.
Conclusion}}{11. Conclusion}}\label{conclusion}}

Aiko\textquotesingle s memory system turns the theoretical account
developed in Paper I into a working, fully auditable pipeline built on
SQLite, sqlite-vec, and FTS5, running comfortably within an 8GB
edge-hardware budget. Six formulas --- decay, entity importance, RRF
fusion, emotional imprinting, supersession, and salience scoring ---
work together to give a system that is tunable without retraining,
explainable at every ranking decision, and lean enough to run
indefinitely on a single-board computer.

Measured against itself, the system meets its own design targets:
\textasciitilde16ms per-turn retrieval latency, \textasciitilde13MB/year
storage growth, a measurable precision gain from multi-signal fusion
over any single signal, and 5.3× monthly compression with no
manually-identified loss of important facts. Measured against the
broader 2026 agentic-memory landscape --- Mem0, Zep/Graphiti, and
Letta/MemGPT --- Aiko occupies a distinct niche: none of the three
general-purpose frameworks are designed first and foremost for a hard
edge-hardware budget and formula-level auditability, and Aiko does not
claim to match their graph-reasoning depth (Zep) or self-managing
runtime sophistication (Letta) on shared benchmarks it has not yet run.
The two design philosophies --- general-purpose, benchmark-optimized
memory services versus a narrow, interpretable, edge-native system ---
are complementary rather than competing, and the appropriate choice
depends on whether the deployment constraint is hardware and
auditability, or benchmark-leaderboard accuracy at cloud scale.
